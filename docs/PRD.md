# Hardware Store Book Keeper — Product Requirements Document

Version 1.0 — As-Built Documentation
Prepared: August 12, 2026
Prepared for: Krrish Talreja

This document describes the `bookkeeper_app` product as currently implemented in the codebase, reverse-engineered from source for use as a shared reference. It is not a forward-looking spec unless noted otherwise.

> **Maintenance note:** This PRD is kept up to date alongside the codebase. When functionality changes (features added/removed, endpoints changed, scope changes), update this document in the same session as the code change.

---

## 1. Overview

### 1.1 Product Summary
Hardware Store Book Keeper is a mobile-first bookkeeping application for small retail and hardware stores. It replaces paper ledgers and ad hoc spreadsheets with a single app that covers billing, customer dues, inventory, supplier purchases, expenses, cash reconciliation, GST return preparation, and staff/account administration. It ships as a Flutter client (Android, iOS, web, Windows, macOS, Linux) backed by a Python FastAPI service, backed by a Postgres database (Neon, serverless) in production, falling back to a local SQLite file when no `DATABASE_URL` is configured (e.g. a bare local dev checkout).

### 1.2 Problem Statement
Small shop owners typically track sales and customer credit ('udhaar') by hand, which makes it hard to answer basic questions quickly: who owes how much, what's running low on the shelf, what today's cash position is, and what the shop owes the tax authority this month. This product gives a single owner-operated shop a phone-based system that answers those questions in real time and prepares GST filings automatically from recorded transactions.

### 1.3 Purpose of This Document
This PRD was produced by reviewing the current source code (Flutter client under `lib/`, FastAPI backend under `backend/`) rather than written ahead of implementation. Its purpose is to give a complete, accurate reference of what the product does today — useful for onboarding a new contributor, planning the next set of features against a known baseline, or handoff/investment conversations.

---

## 2. Target Users
- **Shop owner (primary)** — uses the app day-to-day on a phone to bill customers, track dues, watch stock, and check monthly profit.
- **Cashier / staff** — takes bills, scans items, collects payments, and records purchases from suppliers.
- **Shop admin** — manages user accounts, grants admin access, and configures the API server address via the Admin Panel.

---

## 3. Goals
The product is designed to support the following outcomes for a single-shop operator:
- Record a sale and its sales-tax detail in one flow, without separate bookkeeping afterward.
- Show same-day visibility into outstanding customer dues, cash on hand, and low-stock items without manual reconciliation.
- Prepare a monthly sales-tax report directly from recorded bills, rather than re-entering data into separate tax software.
- Keep bill capture working through short connectivity gaps, which are common in small-shop settings, and sync automatically once back online.
- Let the owner delegate day-to-day billing to staff while keeping account and server-configuration control restricted to admins.

---

## 4. Scope

### 4.1 In Scope
Everything documented in Section 5 (Functional Requirements) below — billing, customers, suppliers, inventory, expenses, reporting, sales-tax reporting, cash reconciliation, notifications, backup/export, settings, admin, and offline bill capture.

### 4.2 Out of Scope (current build)
- Multi-shop / multi-branch operation — the backend is single-tenant per deployment.
- Live FBR e-invoicing / Annex-C integration and Raast merchant payments — both need a business decision (which licensed integrator / bank-PSP) plus a confirmed external schema before they can be built.
- Multi-currency support (amounts are PKR only; the currency word follows the selected language — "Rs" in Latin-script languages, e.g. "1,234 روپے" in Urdu, "रु 1,234" in Hindi).
- Direct POS hardware integration beyond generic PDF invoice printing/sharing.
- Multi-warehouse inventory (stock is tracked as a single quantity per item).

## 5. Functional Requirements

### 5.1 Authentication & Accounts
- The system shall allow sign-up and sign-in with email/password via Firebase Authentication. Sign-up requires name, email, phone, and password — all mandatory. Sign-up does not collect a username; one can be set anytime afterward (see "Change Username" below).
- The system shall allow sign-in with either email or username — a bare username (no "@") is resolved to its email via the backend (`GET /users/resolve-username/{username}`) before the Firebase sign-in call, since Firebase Auth has no native username concept. Username is stored as a Firebase custom claim (set via `POST /users/username`, backend-only — enforced unique) and phone is stored on the Firebase user record (via `POST /users/phone`, backend-only — the client SDK can only set phoneNumber through full SMS/OTP verification).
- The system shall give specific sign-in errors and close the keyboard when Sign In is tapped: an unknown username reads "Incorrect username", a known account with a wrong password reads "Incorrect password", and an unknown email reads "Incorrect email". Firebase gives the same reply for a wrong email and a wrong password, so for an email the app asks the backend (`GET /users/resolve-username/email-exists/{email}`, unauthenticated and rate limited like the username lookup, returns `{exists: bool}`); if that check is unavailable the message falls back to "Incorrect email or password". A wrong email typed together with a wrong password can only be reported as a wrong email, because a non-existent account has no password to check.
- The login and signup screens share a "glass" design (`lib/auth/auth_glass.dart`): a teal (rust in dark theme) gradient with slowly drifting glowing orbs, a frosted-glass logo badge and form card, fields that glow when focused, a white pill primary button that shows a spinner while working, and a staggered entrance animation. The drift and entrance are skipped when the phone's "remove animations" setting is on. In landscape the header collapses to one compact row so the form is visible without scrolling, and the screen scrolls when the form is still taller than the screen. The sign-in logic, validation, remember-me, forgot-password and Google sign-in are unchanged.
- The system shall allow sign-in with Google.
- The system shall let a signed-in account that only has Google as a provider set a password ("Set a Password", Settings → Account), so it can also sign in with email/username + password afterward. Firebase never exposes the linked Google account's real password — this sets a new one the user chooses.
- The system shall let a signed-in account that already has a password change it ("Change Password", Settings → Account) — reauthenticating with the current password first, which Firebase requires for the change and which also verifies the current password is correct.
- The system shall let a signed-in user change their username ("Change Username", Settings → Account), rejecting one already taken by a different account (`POST /users/username`, same backend endpoint sign-up uses to set it initially).
- The system shall let a signed-in user change their email address ("Change Email", Settings → Account) — reauthenticating with their current password first, then sending a verification link to the new address before it takes effect (Firebase requires the new address to be confirmed, not just typed).
- The system shall let a signed-in user unlink a sign-in method (Google or password) from their account, when more than one is linked — Settings → Account shows which provider(s) are currently linked (e.g. a "Google" badge) so the user knows what's removable before attempting it. Unlinking the only remaining sign-in method is not allowed, to avoid locking the account out entirely.
- The system shall let a signed-in user permanently delete their own account (Settings → Account), removing it from Firebase Authentication. This is a destructive, unrecoverable action distinct from an admin disabling/deleting another account (Section 5.14).
- The system shall let a user lock the app behind a PIN and/or biometric (fingerprint/face) unlock ("App Lock", Settings → Account), checked whenever the app returns to the foreground after being backgrounded. This is separate from and in addition to the 24-hour inactivity sign-out below — App Lock re-locks quickly and doesn't sign the user out of their account, it only re-gates access to the already-open session.
- Account (password, username, email, sign-in methods, App Lock, delete account, sign-out) lives on its own screen reached from a Settings nav row, mirroring the Notifications screen's presentation, rather than as an inline card on the Settings screen itself.
- The system shall send and allow resending of email verification.
- The system shall allow the signed-in user to sign out, returning to the login screen.
- The system shall automatically sign a user out after 24 hours of app inactivity (backgrounded or closed), checked at launch and every time the app returns to the foreground — a shop device shared by staff would otherwise stay signed in to one account indefinitely.

### 5.2 Billing & Invoicing
- The system shall let a user create and edit itemized bills tied to a customer.
- The system shall let a user add line items to a bill by scanning a barcode.
- The system shall apply per-item GST/HSN, falling back to the shop's default GST rate/HSN when an item has none set.
- The system shall assign each bill a sequential invoice number scoped to the financial year (format `INV-YY-YY-NNNN`).
- The system shall generate a PDF invoice for any bill, and support printing and sharing it (including via WhatsApp).
- The system shall generate a JazzCash payment QR code for a bill, encoding the shop's JazzCash mobile number so a customer can scan it straight into their JazzCash app's "send money" recipient field rather than typing it by hand. Unlike India's UPI, JazzCash has no interoperable app-launch deep link (UPI is an NPCI-mandated standard every UPI app registers for; JazzCash is a single proprietary wallet), so there's no "pay with app" button — the customer still completes the transfer manually in their own JazzCash app.
- The system shall block saving a real (non-quotation) bill that would push a customer's outstanding balance over their configured credit limit, unless the user explicitly overrides the check for that bill. A customer with no credit limit set (or a limit of 0) is never blocked.
- The system shall let a user save a bill as a quotation, deducting no stock and resolving no GST/cost snapshot until it is converted to a real bill.
- The system shall let a user convert a saved quotation into a bill, at which point stock is deducted and GST/cost are resolved as normal. Converting is one-way: an existing real bill cannot be edited back into a quotation, since that would silently revert its stock deduction and discard whatever amount it had actually collected.
- The system shall let a user return a bill, choosing a quantity per line item (defaulting to the full amount sold), which restores stock for only what's returned and records a linked credit note (a negative-amount bill referencing the original) rather than deleting it. A bill can be returned once; a second, later partial return against the same bill isn't supported. A quotation cannot be returned (it never affected stock or the customer's balance in the first place). A return credit note itself cannot be edited (it records what came back, not a form to retype); deleting it reverses its stock effect correctly, same as deleting a normal bill reverses the opposite direction.
- The system shall let a user repeat a customer's last bill as the starting point for a new one.
- The system shall let a user void a bill with an optional reason — for a mistaken entry (wrong customer, typo, duplicate) rather than an actual return of goods. Unlike deleting, a voided bill stays in the ledger for audit trail with its original amount and line items untouched, but is excluded from every balance/report/GST calculation the same way a quotation is, and its stock effect is reversed once. A quotation, a return credit note, an already-voided bill, or a bill that's already been returned can't be voided; a voided bill can't be edited, returned, invoiced, or have its payment status changed.
- The system shall let a user apply a flat Rupee discount to a bill, clamped to the line-item subtotal (can't go negative or exceed it). The discount is applied after GST — the tax invoice's per-line GST breakup is unaffected, and the invoice PDF shows it as an explicit "Less: Discount" line above Round Off. Every balance, outstanding, and report calculation reads the already-discounted bill amount, so no separate discount-aware code path was needed there.
- The system shall let a user email a bill's tax invoice directly to the customer's email on file, using the shop's own SMTP account (configured once by an admin — see 5.14). Rejected with a clear message if the customer has no email on file or SMTP hasn't been set up yet; guarded the same way as viewing/printing the invoice (not available for a quotation or a voided bill).
- The system shall let a user create a bill by photographing a handwritten paper bill (Sindhi, Urdu, or English script, in any mix) instead of typing it in. The photo is sent to Google Gemini to extract a customer name, date, and line items; the extracted customer name is matched against existing customers (exact match auto-selected, a close spelling variant offered as a confirm-first suggestion, no match prompting the user to create a new customer) before the extraction lands on the normal Add Bill screen, prefilled, for the user to review and edit like any other bill — nothing is saved automatically. The original photo and the raw extraction are kept on the resulting bill (`image_url`/`raw_extraction`) as an audit trail. Requires `GEMINI_API_KEY` configured server-side (see Section 8); the scan endpoint returns a clear error rather than a bare failure when it isn't. Both scanners (bills and purchase invoices) first check that the photo really is a bill/invoice: the model reports `is_document`, and a photo with that false, or with no readable line items, is rejected with HTTP 422 `not_a_bill` before it is stored or any customer is suggested; the app then shows a translated "doesn't look like a bill/invoice" message instead of the new-customer prompt.
- The system shall let a user start a new bill directly from the Home dashboard's "New Bill" button without picking a customer first, for a quick counter sale where recording who bought it doesn't matter — it bills against a standing "Walk-in Customer" record, created automatically the first time it's needed.

### 5.3 Customer Management
- The system shall let a user add, edit, and delete customers, including name, phone, credit limit, STRN (validated against the standard 13-digit STRN format), address, and email.
- The system shall let a user bulk-import customers from a CSV file (header row: name, and optionally phone / credit_limit / strn / address / email) — every row becomes a new customer, with no de-duplication.
- The system shall show a customer list and a per-customer detail view with full bill and payment history.
- The system shall provide a Collect Money flow to record a payment against a customer's outstanding balance, applying it to their oldest unpaid bill(s) first and splitting across bills when the amount doesn't match one exactly. The system shall reject an amount exceeding the customer's current outstanding balance, and reject collection when nothing is owed, rather than over-applying it. A bill only becomes "paid" once fully covered; a partially-covered bill stays "unpaid" with the reduced balance shown in the bill list, since every outstanding/aging figure is derived from amount owed, not the status label.
- The system shall let a user tap a bill's (or, mirrored on the supplier side, a purchase's) status chip to toggle it between paid and unpaid directly, without going through Collect Money — guarded the same way (not for a quotation/PO, a return credit note, or a voided bill). Marking one paid plays a one-shot "PAID" ink-stamp animation over the card (haptic + sound) before settling back to the plain status chip; marking one unpaid again is a plain instant flip with no animation.
- The system shall let a user generate a PDF account statement (ledger) for a customer, and email it directly to their email on file using the shop's own SMTP account. Rejected with a clear message if the customer has no email on file or SMTP hasn't been set up yet.
- The system shall provide a Dues Center listing every customer with an outstanding balance, bucketed by days since their oldest unpaid bill (0–30 / 30–60 / 60+).
- The system shall let a user send a payment reminder to a customer via WhatsApp, SMS (native `sms:` composer, prefilled), or plain text share, with a choice of tone (polite/standard/urgent) and an optional JazzCash payment QR preview, from either the Dues Center or the customer detail screen.
- The system shall provide search across customers and bills.
- The system shall let a user filter the customer list by name or phone inline, and sort it alphabetically or by most-recently-added.
- The system shall let a user assign a price tier (retail, wholesale, or contractor) to a customer, defaulting to retail. Used only to decide which of an item's prices Add Bill pre-fills for that customer (see 5.5) — not enforced server-side, so the price on any line stays freely editable either way, same as every other price in this app.
- The system shall group the customer list into "Owes Money" and "Settled Up" sections (only when both are non-empty) and show a running total of customers and outstanding balance above the list. A customer with a credit limit set shows a usage bar (limit used vs. remaining) inline. Customers added in the last 7 days carry a "New" tag.
- The system shall let a user call or open a WhatsApp chat with a customer directly from the customer list (when a phone number is on file), and start a new bill for a customer via a right-swipe on their row, without opening their detail screen first. Edit and delete are reached via a three-dot Actions sheet on the row (also reachable via left-swipe-to-delete). A user may also long-press to multi-select customers and bulk-delete them.
- The system shall let a user select multiple customers from the list (via long-press) and delete them together with their bills, with a "Select All" / "Deselect All" shortcut across the currently filtered list.
- The system shall open a bill's (or, on the supplier side, a purchase's) full details in a bottom sheet when its card is tapped: a gradient hero with a status pill (PAID / PARTIAL / UNPAID / VOIDED / RETURN / QUOTE for bills; PAID / PARTIAL / UNPAID / DRAFT PO / RETURN for purchases), the amount and the date; Total / Paid / Remaining (Payable for purchases) tiles for real bills and purchases (hidden for voided bills, returns, quotes and draft POs); and a card of every line item with quantity × rate, any discount, and the total. The sheet sizes to its content rather than a fixed height. Both screens use one shared widget, `lib/widgets/document_sheet.dart`.

### 5.4 Supplier & Purchase Management
- The system shall let a user add, edit, and delete suppliers, including name, phone, STRN (validated against the standard 13-digit STRN format, same as for customers), and address.
- The system shall let a user bulk-import suppliers from a CSV file (header row: name, and optionally phone / strn / address) — every row becomes a new supplier, with no de-duplication.
- The system shall let a user record a purchase against a supplier, which updates item stock on save.
- The system shall let a user return some or all of a purchase's line items to the supplier, choosing a quantity per line (defaulting to the full amount purchased), which removes stock for only what's returned and records a linked credit note (a negative-amount purchase referencing the original) rather than deleting it — mirrors returning a bill. A purchase can be returned once; a second, later partial return against the same purchase isn't supported. A return credit note itself cannot be edited or returned again; deleting it correctly reverses its stock effect, same as deleting a normal purchase reverses the opposite direction.
- The system shall show a per-supplier purchase ledger.
- The system shall provide a Supplier Dues Center listing every supplier with an outstanding payable balance, bucketed by days since their oldest unpaid purchase (0–30 / 30–60 / 60+), mirroring the customer Dues Center.
- The system shall let a user filter the supplier list by name or phone inline, and sort it alphabetically or by most-recently-added.
- The system shall let a user select multiple suppliers from the list (via long-press) and delete them together with their purchases, with a "Select All" / "Deselect All" shortcut across the currently filtered list. Swipe gestures are disabled while selecting.
- The system shall let a user call or open a WhatsApp chat with a supplier directly from the supplier list (when a phone number is on file), mirroring the customer list's identical capability.
- The system shall let a user record a purchase by photographing a supplier's purchase invoice/delivery challan instead of typing it in — same AI Bill Scanner engine as Section 5.2's bill scanner (Claude extraction, supplier-name matching with exact-auto/suggest-confirm/create-new, item matching, review on the normal Add Purchase screen before anything saves, original photo + raw extraction kept on the resulting purchase as an audit trail, offline queueing). See Section 5.2 for the shared mechanics; the only difference is what's extracted (a supplier name and cost-price line items, from a purchase invoice) and where it lands (`POST /purchases/scan`, `Purchase.image_url`/`raw_extraction`).
- The system shall let a user save a purchase as a draft Purchase Order instead of a real purchase — no stock added and no cost-price update until it's explicitly marked received (`POST /purchases/{id}/convert`), mirroring the bill quotation pattern in Section 5.2. A draft PO is excluded from payables aging, the Sales Tax monthly summary's input tax credit, and the supplier ledger, the same way a quotation is excluded from their bill-side equivalents, and shows a distinct badge in the supplier's purchase list. Converting is one-way — an already-received purchase can't be edited back into a draft PO — and a draft PO can't be returned, since nothing was actually received yet.

### 5.5 Inventory / Items
- The system shall maintain an item catalog with name, unit, price, category, HSN code, GST rate, stock quantity, and a low-stock threshold.
- The system shall support bulk-adding items and bulk stock updates. Bulk-add matches existing items by name (case-insensitive) and, for a match, updates only the fields the line actually supplied — price (when non-zero), unit and category (when non-empty) — leaving stock, cost price, HSN and GST untouched; unmatched names are created as new items (`backend/test_bulk_items.py`).
- The system shall support looking up an item by barcode.
- The system shall detect and help resolve duplicate item entries.
- The system shall surface low-stock items on the dashboard and via a notification trigger.
- The system shall let a user attach a photo to an item, captured via camera or chosen from the gallery, shown as a thumbnail in the item list in place of the default letter avatar — uploadable directly from the list row (no Edit screen round trip), and viewable full-size by tapping the thumbnail.
- The system shall let a user select multiple items from the list (via long-press) and delete them together, with a "Select All" / "Deselect All" shortcut across the currently filtered list.
- The system shall let a user duplicate an existing item as a starting point for a new one (e.g. a size/weight variant) — copying its name, price, unit, category, and tax fields, but never its stock quantity, barcode, or photo, each of which must be its own for the new item.
- The system shall visually distinguish an out-of-stock item (zero quantity) from a merely-low-stock item in the list, and offer a "Low Stock" quick-filter chip alongside category filters.
- The system shall let a user set a preferred supplier per item, used to one-tap reorder that item from the low-stock list (pre-filling a purchase against the preferred supplier at a system-suggested quantity — see below).
- The system shall suggest a reorder quantity per low-stock item, shown on the low-stock list and used to pre-fill the one-tap reorder purchase: for an item with sales in the last 30 days, enough to cover ~14 days at its recent average daily sales rate; for an item with no recent sales, enough to bring stock back up to its low-stock threshold.
- The system shall let a user reorder every low-stock item with a preferred supplier in one action ("Reorder All"), grouping them by supplier into one pre-filled multi-item purchase per supplier (a quick picker appears first when more than one supplier is involved).
- The system shall let a user send a WhatsApp message to an item's preferred supplier with its suggested reorder quantity — either for a single low-stock item, or for every low-stock item with a preferred supplier at once ("WhatsApp All", grouped by supplier the same way as "Reorder All"). Opens WhatsApp pre-filled with the message; falls back to the system share sheet if WhatsApp isn't installed/reachable.
- The system shall log every manual stock-count correction made via Update Stock as a dated, attributed entry (previous quantity → new quantity, who made it), viewable per item as its "Stock Adjustment History" (a timeline with a current-stock summary card, net-change chip and trend line) — written only for an item whose count actually changed, leaving an unaffected item's history untouched. Each entry also shows its exact time (in the viewer's time zone) and an optional note typed on Update Stock ("Note (optional)", shown once any quantity has changed, applied to every item changed in that save, up to 200 characters). A user with the void/delete/return permission (or an admin) can edit one entry's quantities and note, remove one entry, or reset the whole history; these change only the record, never the item's real stock. "Send as PDF" opens a print/share PDF of the history in the app's language and digits.
- The system shall provide a Stock Valuation Report showing the total value of stock currently on hand (quantity × cost price, falling back to selling price for items with no recorded cost), broken down by category and by item.
- The system shall track an item's selling price and cost price over time, logging a new entry whenever either actually changes (on item edit, or when a purchase updates the item's cost price) — never on unrelated field edits. A "Price History" view per item shows this log as a timeline (newest highlighted) under a summary card with the current price, the % change since the first entry and a trend line, with an up/down/flat indicator against the previous entry, to help spot creeping costs or forgotten price updates. Each entry also shows its exact time and who made the change (including purchase-driven cost changes). A user with the same permission can edit one entry's price and cost price, remove one entry, or reset the whole history — only the record changes, never the item's real price — and "Send as PDF" shares the history as a PDF.
- The system shall let a user print a barcode label (40×25mm, name/price/barcode) for a single item from its list row or edit screen, or bulk-print labels for a chosen subset of items with a barcode in one combined print job.
- The system shall let a user download a shareable rate-card PDF (`GET /items/rate-card`) — every item's name/unit/price grouped by category (units and column headers in the PDF language), with the shop's logo and name, for handing or messaging to a customer who asks for pricing. Distinct from an invoice or ledger: no transaction data, just a current price list.
- The system shall let a user optionally set a wholesale price and a contractor price per item, alongside its normal retail price — each falls back to the retail price when left unset. Add Bill pre-fills whichever price matches the bill's customer's price tier (see 5.3); the line's price stays freely editable regardless of which one was pre-filled.
- The system shall let a user search the item list by voice (microphone icon next to the search field) as an alternative to typing, for use when hands are dirty or gloved.
- The system shall show, when editing an item, a "Frequently bought with" list of other items that most often appear on the same bill as this one — a plain co-occurrence count from past sales, not a recommendation engine.

> **Seed data note:** As of 2026-08-13, 103 of the 105 items in the current dev database have a photo populated (sourced from Wikimedia Commons via a one-off backend seeding script, not an in-app feature — the app itself only supports camera/gallery upload). The remaining 2 (Hacksaw Frame, Hooks Wall Small) have no suitable free-licensed photo available and fall back to the letter avatar, same as any item without a photo.

### 5.6 Expense Tracking
- The system shall let a user log, edit, and delete expenses, each with a category.
- The system shall show an expense breakdown by category on the dashboard and in reports.
- The system shall let a user mark an expense as monthly-recurring (e.g. rent, electricity) and shall remind the user, on the Expenses screen, of any recurring expense whose most recent occurrence isn't in the current calendar month, with a one-tap prefilled quick-add for that month's occurrence. There is no server-side scheduler — generation is on-demand and client-driven.
- The system shall let a user attach a receipt photo (camera or gallery) to an expense when adding or editing it; the Expenses list shall show a receipt indicator on any expense with one attached, tappable to view the full photo. Like item photos (see Section 5.13), a receipt picked while offline is queued alongside the expense write and uploads automatically once that write syncs.

### 5.7 Reporting & Dashboard
- The system shall present a home dashboard with Overview, Stock, and Money tabs.
- The system shall show this month's sales total and this month's profit (revenue minus cost of goods sold minus expenses), alongside a bar-chart trend of profit over the last several months.
- The system shall show total outstanding balance and a breakdown by customer.
- The system shall show top items by quantity sold and by revenue, and top customers by revenue.
- The system shall show profit (revenue minus cost of goods sold) broken down per item and per category, all-time, ranked by profit rather than by revenue — surfacing items that sell a lot but earn little margin, or sell rarely but earn a lot per unit, which the revenue-only rankings can't show.
- The system shall show an expected cash-on-hand figure for today.
- The system shall let a user ask a plain-English question about the business ("Ask Your Shop", reached from a bottom-right icon on the Home dashboard) and receive a short (2–4 sentence) answer, written by Google Gemini strictly from a snapshot of the same figures Reports already computes (recent sales/profit, expenses by category, stock valuation, top items, low-stock items, customer dues) — the model never runs its own query and can't touch data outside that snapshot, and the prompt forbids inventing any number, name, or event not present in it. Supports typed or voice input (speech-to-text) and speaks the answer back in a human-sounding voice: the app first asks the server to read it with Gemini text-to-speech (`POST /reports/speak`, free tier, 60 requests/hour per client (an answer uses up to two), any app language, `GEMINI_TTS_MODEL` / `GEMINI_TTS_VOICE` configurable; a voice icon in the Ask Your Shop sheet header opens a settings sheet where the user picks one of nine voices — five female (Leda, Aoede, Zephyr, Sulafat, Despina) and four male (Puck, Charon, Fenrir, Orus), marked by a female/male icon, plus a pace (Slower / Normal / Faster) and a tone (Calm / Warm / Cheerful); all three are remembered on the device and closing the sheet re-reads the answer on screen once if anything changed; the server accepts only those voice, pace and tone values and passes pace and tone to Gemini as its structured `speech_metadata.style` (Interactions API), never inside the spoken text, because Gemini 3.8 reads the text field verbatim and an instruction placed in it is announced aloud; to start speaking sooner the app voices the first sentence while the rest is fetched, then plays the rest right after; the server sends the audio as MP3 (about 8x smaller than Gemini's WAV, which was most of the wait on mobile data); the API key travels in a request header and never appears in an error message) and plays the returned audio; if that fails (offline, free limit reached: on the free tier `gemini-3.8-flash-tts` allows only about 10 requests per day, and the first-sentence split uses two per answer) it falls back to the phone's best installed voice for the app language (Google network/neural voices preferred), and a small note under the answer says "Reading this with your phone's voice." (translated) so the different sound is explained, with "Rs 1,234" read as "1,234 rupees". A loading state shows one of several animated "thinking" dot-sphere styles, randomly picked per question, with a status label under the orb that cycles through varied phrases ("Working on it…", "Crunching the numbers…", "Checking your books…", etc.) every couple of seconds rather than a single fixed "Thinking…". Answers state money in rupees ("Rs 1,234"), never "$". Requires `GEMINI_API_KEY` configured server-side (a free-tier Google Gemini key); returns a clear error rather than a bare failure when it isn't configured, and retries once automatically on a rate-limit/transient server error before surfacing one to the user.
- The Home Overview tab shall show an AI Briefing card that presents only a "Get Briefing" button until the user presses it — nothing is fetched or generated when Home opens, and the last briefing saved by the daily job is no longer pre-loaded. Pressing the button generates a fresh AI Morning Briefing (subject to the AI-route rate limit in §6.3); once shown it stays for the rest of the app session, and a small refresh icon on the card regenerates it.

### 5.8 Sales Tax Reporting
- The system shall generate an outward-sales invoice-detail report and a monthly summary report for a selected month, viewable in-app and exportable as CSV. Pakistan sales tax is single-rate — no interstate/intrastate CGST/SGST/IGST split. These are internal bookkeeping reports for the shop's own records, not a claim that they match FBR's official Sales Tax Return/Annex-C format, which hasn't been confirmed.
- The system shall provide invoice-wise tax detail backing the summary reports.
- The system shall apply per-item tax rate/HSN to purchase line items the same way it does for bills (explicit → catalog item → shop default), and use it to compute the monthly summary's Input Tax Credit — a returned purchase's ITC nets back out automatically. The monthly summary's net payable is outward tax minus total ITC.

### 5.9 Cash Reconciliation
- The system shall provide a daily cash reconciliation screen comparing expected cash against a manually counted amount.
- The system shall show today's non-cash collections (bank transfer, cheque) alongside the cash figure, for context — informational only, not part of the drawer count/compare, since only physical cash gets counted against a drawer.

### 5.10 Notifications
- The system shall deliver push notifications via Firebase Cloud Messaging.
- The system shall provide a Smart Notifications screen with four independently toggleable, manually triggerable checks: low-stock alerts, overdue-payment reminders, a daily business summary (sales, collections, profit), and an AI Morning Briefing.
- The system shall run all four checks automatically once per calendar day on the server, in addition to the manual "Check Now"/"Send…" triggers above, independent of whether anyone has the app open.
- The AI Morning Briefing shall synthesize yesterday's sales/collections, current low-stock items, overdue payments, and pending purchase orders into a short (2–4 sentence) plain-English handover, written by Google Gemini strictly from those computed figures — the prompt forbids adding any number, name, or event not present in them, and requires amounts in rupees ("Rs 1,234"). Requires `GEMINI_API_KEY` configured server-side (see Section 8); returns a clear error rather than a bare failure when it isn't configured, or when the API call itself fails (e.g. no credit balance, rate limit).

### 5.11 Backup & Data Export
- The system shall let an admin download a full backup of shop data and restore from a backup file, with a safety copy of the current data kept server-side before a restore overwrites it. Downloading or restoring the full database is admin-only — it carries every customer's financial and contact data, and restoring replaces the entire shop's data outright, unlike the CSV exports below, which stay available to any signed-in staff member. The backup format depends on the active database: a single SQLite database file on the fallback (`.pre_restore.bak` kept alongside it), or a JSON dump of every table — built from SQLAlchemy's own schema metadata, not `pg_dump` — on a Postgres deployment (a timestamped `pre_restore_*.json` kept in the same backups folder). Either format restores through the same `GET /backup` / `POST /backup/restore` endpoints; the two aren't cross-compatible with each other. Neon's own point-in-time restore/branching remains available as a separate, database-level recovery option.
- The system shall let a user export customers, bills, items, expenses, stock valuation, and supplier dues to CSV.
- The system shall let a user restrict the Bills and Expenses CSV exports to a chosen date range (the only two exports with a natural transaction date — the others are point-in-time snapshots), picked with a standard date-range picker; the exported filename reflects the range used, and an unset range exports everything as before.
- The system shall automatically write a full database backup once per calendar day on the server, retaining the most recent 14 and pruning older ones — an always-on safety net that runs whether or not anyone has the app open, separate from the on-demand download above, in the same format (SQLite file copy or JSON table dump) as the manual download. An admin can see how many are stored and when the most recent one ran; there is no restore-from-history flow through the app on purpose — recovering from one is a same-machine file-copy job for whoever runs the server. On a serverless Vercel deployment there is no persistent disk, so a daily Vercel Cron job (`/internal/cron/backup`, 04:30 UTC) instead writes the Postgres JSON dump to Vercel Blob under `backups/`, encrypted with `BACKUP_ENCRYPTION_KEY` (Fernet) because the Blob store is public — with no key set it skips with a logged warning rather than upload plaintext. The same 14-day retention applies, and `backend/restore_backup.py` fetches and decrypts the newest (or a dated) backup into a plain JSON file for restore. The key must also be kept somewhere other than the server: without it the backups are unreadable. The database provider's point-in-time restore remains a second safety net; the on-demand download still works. Covered by `backend/test_blob_backup.py`.

Once the JazzCash number is valid, a small QR appears inside the field itself, just after the number; it redraws on every keystroke so it always matches what is typed, and tapping it opens a large, scan-ready popup with the shop name, the formatted number and a Copy number button. Nothing QR-related takes up screen space otherwise; a one-line "Looks good" / "Check the number" status shows under the field while typing. The Items screen's Price History and Stock Adjustments popups share one sheet design (`showHistorySheet`): drag handle, icon-badge header with the item name, each entry as a rounded card with a trend icon and a change pill (+/-), and an illustrated empty state. Confirmation dialogs and any bottom sheet without its own styling also use app-wide themes (`appDialogTheme`, `appBottomSheetTheme`: rounded, softly lifted, bold titles, drag handle on sheets). Every in-app message (SnackBar) uses one app-wide theme (`appSnackBarTheme`): a floating, rounded, softly lifted card in a deep tone, with an icon badge on the scan messages (warning for "not a bill", check for saved). The Settings banner shows the shop name with the signed-in account's username underneath (falling back to the email only when the account has no username), and refreshes after the Account screen is closed. - The system shall let a user upload a shop logo (camera or gallery), shown on the invoice PDF and both customer/supplier ledger PDFs, replacing any previously uploaded logo. Before one is uploaded, the logo picker shows the app's own icon as a placeholder rather than a generic add-photo icon.
- The system shall let a user switch between light, dark, and system theme.
- The system shall let a user update the app from inside the app (Android release builds): Settings → Tools & Sync → App update, and a silent check at launch, ask the backend (`GET /app/latest`, login-required) for the newest published build, and if its build number is higher than the installed one offer to download the APK and hand it to the system installer. Android asks once to allow installs from Book-Keep. The update prompt also offers Save to Downloads, which stores the APK as `Book-Keep-build-N.apk` in the public Downloads folder without installing it. CI (`.github/workflows/release-apk.yml`, run manually) builds the signed APK with build number = run number + 1000 (above the +100 builds an earlier repo published), takes the backend address from the `BASE_URL` repository secret, uploads it to Vercel Blob under `app-releases/` with an unguessable URL and keeps the newest two. Only APKs signed with the same key can update each other, so the first release build needs the debug app uninstalled. Debug builds skip the automatic check.
- The system shall let a user choose the app's display language from a full-screen picker listing every supported language by its native name (see Section 6.1), persisted per device and applied immediately; the picker has a search field to filter the list by display name.

### 5.13 Offline Support
- The system shall queue a bill locally on the device (SQLite) when it cannot be created or edited due to no connectivity.
- The system shall queue a customer, item, supplier, or purchase create/edit, an expense create/edit, a bill payment-status update, or a Collect Money payment locally when it cannot reach the backend.
- The system shall automatically retry all queued writes when connectivity returns, and also allow a manual sync trigger.
- The system shall show a combined pending-sync count and status on the dashboard while any write is queued.
- The system shall silently re-fetch an already-open list screen (Home dashboard, Items, Customers, Suppliers, Expenses) when a background sync just pushed or pulled something, so it doesn't keep showing stale data (or a stale connection-error message) until the user manually pulls to refresh.

> **Note:** Offline queuing covers bills, customers, items, suppliers, purchases, expenses, bill payment-status updates, and Collect Money payments — every create/edit form in the app, plus this one payment-collection action. Unlike a payment-status toggle (which knows exactly which bill and value to set), a queued Collect Money payment's oldest-first allocation across bills is resolved server-side once the write actually syncs — the app can't show which bill(s) it landed on until then. A picked item photo or expense receipt photo queues alongside its create/edit write and uploads automatically right after that write syncs (a new item or expense has no server ID to attach a photo to until then). Creating a bill (or a purchase) offline for a customer (or item) that was *also* created offline in the same session isn't supported — the referenced record needs a server-assigned ID first.

- The system shall queue a bill or purchase-invoice photo picked for AI scanning (Sections 5.2/5.4) locally when it cannot reach the backend, and send it for extraction automatically once connectivity returns — each in its own queue (`pending_scans` / `pending_purchase_scans`), separate from the `pending_writes` queue above, since a scan has nothing to push until Claude has actually read it. The Scan Bill/Scan Purchase Invoice screens each list their own queued/ready/failed scans so a picked photo is never lost; a failed scan can be retried individually.

### 5.14 Admin Panel
- The system shall let an admin view, create, edit, disable, and delete user accounts. The account list shows each account's phone number and username alongside email/name, when set.
- The system shall let an admin grant or revoke admin access for another account.
- The system shall restrict all admin functionality to accounts the backend recognizes as admins, returning an access-denied state to everyone else.
- The system shall prevent an admin from deleting, disabling, or revoking admin access from their own account, to avoid a self-lockout with no way back into the panel.
- The system shall let an admin view a staff activity log recording who (by email/name, when identifiable) did what, for accountability when multiple people share the shop account. Only sensitive/hard-to-reverse actions are recorded — voiding a bill, deleting a bill, returning a bill, deleting a customer, deleting a supplier, and admin account changes (create/update/delete) — not every read or routine edit.
- The system shall let an admin grant a non-admin account a separate "can manage" permission — independent of admin access — allowing it to void, delete, or return a bill or purchase; delete a customer, supplier, item, or expense; or merge duplicate items. Before this permission existed, any authenticated account could do all of these; a plain staff account without it is now rejected. An admin always has this implicitly, regardless of the flag.
- The system shall let an admin configure the shop's own SMTP email account (host, port, address, password, optional display name) so any signed-in staff account can then email an invoice or customer statement. This is kept separate from the general shop settings (5.12), which any signed-in account can currently write — an SMTP password has no business being reachable there. The password is never returned once saved; the panel only shows whether email is configured, and re-saving other fields without retyping the password leaves it unchanged.
- The backend shall enforce a per-client-IP rate limit (currently 120 requests/minute, in-memory sliding window) on every request, returning HTTP 429 once exceeded — a basic abuse/runaway-client guard, not a billing or quota feature.
- The backend shall enforce a stricter per-client-IP rate limit (currently 10 requests/hour) specifically on the four routes that call Gemini (bill scan, purchase-invoice scan, Ask Your Shop, AI Morning Briefing), and a separate 30/hour limit on reading an answer aloud — the general 120/minute limit protects the server, not the shop's free Gemini quota from one account hammering just these.

## 6. Non-Functional Requirements

### 6.1 Platform & Compatibility
- Single Flutter/Dart codebase targeting Android, iOS, Web, Windows, macOS, and Linux.
- The backend is plain HTTP only, reached at a raw LAN/emulator IP literal, never a real hostname (see 7. Technical Architecture) — every platform needs its own explicit opt-in to allow that: Android's `usesCleartextTraffic="true"` (set only in the debug manifest, so release builds accept HTTPS only), iOS/macOS's `NSAppTransportSecurity` → `NSAllowsLocalNetworking`, and (macOS only, since it's sandboxed) the `com.apple.security.network.client` entitlement. Windows/Linux desktop builds aren't sandboxed and need no equivalent.
- Material 3 design system with light, dark, and system-following themes.
- The app is usable in landscape as well as portrait. On a landscape phone (about 360 dp tall) the Home dashboard, the Items, Customers and Suppliers tabs and the customer and supplier detail screens scroll their header (hero card, search, summary, category chips) together with the content instead of pinning it, so the content gets the full height; the Add Bill, Add Purchase and Update Stock screens put their totals/actions panel to the right of the item list; the PIN lock screen and the payment-reminder, collect-payment and Ask Your Shop sheets scroll when they don't fit. Portrait layouts are unchanged. `test/landscape_layout_test.dart` guards these cases.
- UI text is localized into 20 languages (English, Hindi, Urdu, Sindhi, Punjabi, Pashto, Bengali, Arabic, Farsi, Spanish, French, German, Portuguese, Russian, Turkish, Swahili, Indonesian, Japanese, Korean, Chinese) via `flutter_localizations`/`intl` (`lib/l10n/app_*.arb` source strings, generated `AppLocalizations`), user-selectable from Settings → Language and persisted per device. Screens read their text through `context.t.<key>` (`lib/l10n/l10n.dart`); every user-facing screen is translated: the nav bar, Home, Settings, Customers, Customer detail, Items, Suppliers, Supplier detail, Add/Edit forms, Add Bill, Add Purchase, scan screens, Dues, Collect Payment, Update Stock, Search, Reports, Expenses, GST report, Reconciliation, Profit by Item, Stock Valuation, Backup, Notifications, App Update, Account, Admin, login/sign-up and the shared widgets. A few texts stay English on purpose (see Known Limitations). `test/l10n_test.dart` fails if any language is missing a key or a shared widget stops following the selected language. Sindhi has no official Flutter framework-level translation, so framework chrome (date pickers, text-selection toolbar) falls back to Urdu via a custom delegate (`lib/l10n/sindhi_fallback_localizations.dart`) while the app's own strings still render in Sindhi. Item, customer, supplier and category names, and the shop's own name and address (data the shop typed), are shown in the selected language too; in Settings the shop name and address boxes themselves show the selected language's wording, and editing them there saves that language's own wording (`PUT /translate/override`) without touching the base name: the server asks Gemini for a rendering once per name per language (`POST /translate`, `backend/utils/name_translate.py`, cached in the `name_translations` table so each name is only translated once), the app keeps the results on the phone (`lib/name_translator.dart`, read through `context.itemName/partyName/categoryName`) and the PDFs print them. Only what is shown changes: edit forms, search keys, WhatsApp/SMS messages and what is saved keep the name as typed, and search matches both. If Gemini is busy or out of quota the typed name shows and the app asks again a couple of minutes later. Otherwise this is UI-string localization — the tax rate/STRN wording is not itself translated per rule regardless of selected language; the currency word follows the selected language (`formatMoney` in `lib/widgets/money.dart`; Latin-script languages keep "Rs"), and the standard item units are shown translated (`context.unitName`) while the stored value stays English.
- In Arabic, Persian, Pashto, Urdu, Sindhi, Bengali, Hindi and Punjabi every digit the app draws is shown in that language's own digits. The text stays plain 0-9 (so parsing, search and typing are unchanged); the theme lists a digits-only font for the language first (`lib/digit_font.dart`, fonts in `assets/fonts/digits/` built by `scripts/build_digit_fonts.py` from the OFL Noto fonts, with the signs and separators used inside numbers copied from Roboto) with Roboto behind it. PDFs convert the same digits in `backend/utils/pdf_font.py`, leaving a "+country-code" phone number plain. Translated item names also translate their unit words (inch, mm, kg, ft, ...): a short per-language unit list is saved like other names (`name_translations`, kind `unit`) and swapped in after any number, which also repairs names saved earlier. The Ask Your Shop and morning-briefing answers are given the saved translated item, category and customer names, so they cite the names the user sees.
- Navigation between the 6 main sections (Home, Customers, Items, Suppliers, Reports, Settings) is a floating pill-shaped bottom nav bar, not a drawer/hamburger menu. The pill uses a light glassmorphism treatment (translucent white fill, backdrop blur, soft border) built by hand rather than the shared `GlassContainer`, with dark icons/labels for the unselected state (a primary-filled circle + white icon for the selected one) and safe-area-aware bottom padding.
- Cards, buttons, and filter chips use a frosted-glass ("glassmorphism") visual treatment — translucent fill with backdrop blur — applied via shared widgets (`AppCard`, `AvatarListRow`, `GradientButton`, `CategoryChip`) so the look is consistent app-wide.
- App launch shows a branded animated boot splash (`lib/auth/auth_gate.dart`) while a previous Firebase session is restored: the real app icon sits in a frosted-glass badge (real backdrop blur, not a flat color), then "Book-keep" pops in letter-by-letter with an elastic bounce alternating theme colors, a wavy two-tone line draws itself in underneath, and three sparkles finish it off — silently, with no sound effects. Held for a minimum ~2.2s so it's always seen at least once even when the real restore check finishes sooner. A generated native Android/iOS launch screen (via `flutter_native_splash`, configured in `pubspec.yaml`) matches the same brand colors/mark so there's no blank OS screen before it. On Android 12+, the app also registers its own light/dark preference with the OS (`UiModeManager.setApplicationNightMode`, `lib/native_theme.dart`) so this native pre-Flutter screen matches the user's in-app theme choice even when it differs from the device's system setting.

### 6.2 Reliability & Degradation
- The app continues to function if Firebase isn't configured on a given install — push notifications are simply disabled rather than the app failing to start.
- Backend admin routes respond with 503 when the Firebase service account isn't configured, and 403 for authenticated non-admin users, rather than exposing admin data.
- The pooled Neon connection (`backend/database.py`) uses `pool_pre_ping` (discard and silently reconnect a connection Neon's serverless proxy already killed) plus `pool_recycle=280` (proactively retire any pooled connection older than that, under Neon's own ~5-minute idle timeout) — closing the gap where pre_ping alone can still race a connection Neon kills between the ping and the query actually running, which otherwise surfaces as an unhandled "server closed the connection unexpectedly" error to the caller.
- `backend/config.py` strips a leading byte-order mark and surrounding whitespace from every environment value before anything reads it. Values set from Windows tooling can arrive as e.g. `"﻿18"`, which used to crash `float()` at import and turn every Vercel request into a 500 `FUNCTION_INVOCATION_FAILED`; covered by `backend/test_env_clean.py`.
- The app's HTTP layer (`lib/api.dart`) sends every JSON request through one shared client, so requests reuse keep-alive connections instead of paying a fresh TCP + TLS handshake each time. A GET that lands on a kept-alive socket the server already closed is retried once on a fresh connection; writes are never retried automatically. The multipart uploads (photos, scans, backup/restore) still build their own request.
- Keyboard focus is cleared when the user switches main-nav tabs (`MainNavScreen._goTo`) and whenever any route is pushed — popup menu, dialog, bottom sheet or screen (`_UnfocusOnPush` in `main.dart`). The main sections are kept alive in an `IndexedStack` and Android's back gesture hides the keyboard without unfocusing the field, so without this a search field could regain focus (and pop the keyboard up) when a popup closed or a tab changed.
- Launch loads Home first: only the Home section is built up front, and the other five main sections (Customers, Items, Suppliers, Reports, Settings) are built one after another in the background starting about 2.5 s later (or immediately if the user opens one sooner), then stay alive as before. Building all six at once made Home's first requests compete with about 35 others and kept the UI thread busy for over a second. In addition, identical GET requests already in flight share one response (`lib/api.dart`); any write clears the sharing so a read that starts after a write is never served older data.
- Backend startup skips the schema check when nothing changed: `migrations.ensure_schema()` computes a fingerprint of every table/column the models declare plus `migrations.py`'s own source, compares it to the single row in the `schema_meta` table, and only when it differs (or the table is missing) runs `create_all`, the column migrations, the barcode backfill and the settings seed, then stores the new fingerprint. Previously every cold start ran about 130 read-only statements before answering its first request, which on Vercel showed up as ~10 s stalls after the server had been idle. The fingerprint lives in its own table, not in `settings`, because the settings table is read in full into the shop settings. Concurrent first starts tolerate racing to create the table and store the row.

### 6.3 Security
- User authentication is delegated to Firebase Authentication (email/password and Google Sign-In).
- Admin access is gated server-side by an admin email allow-list (only for accounts whose Firebase email is verified) / Firebase custom claims, not by client-side checks alone.
- Sign-up is open by design: anyone can install the app and create an account with no admin approval; the app is single-tenant, so every account sees the same shop data, while void/delete/return/reset/edit actions still need the `can_manage` permission or admin.
- The Android app opts out of cloud backup (`allowBackup="false"`), and the backend pins PyJWT >= 2.15.0 and urllib3 >= 2.8.0.
- Every file-upload endpoint (item/expense/logo photos, bill/purchase AI scans, full-database restore) rejects an oversized upload with HTTP 413 via a shared `utils/uploads.py` guard, rather than buffering an unbounded body into memory.
- Uploaded photos (item, expense receipt, shop logo, bill/purchase scans) are stored on local disk in development and in Vercel Blob when `BLOB_READ_WRITE_TOKEN` is configured (the production/Vercel setup, since Vercel's disk is ephemeral): each upload gets a unique public https URL so a replaced photo is never served stale, and the previous file is removed only after the new one is stored. If Blob is unreachable the upload fails with a clear 502 and the existing photo is kept. Bill and purchase scan photos — attached only as an audit trail and never displayed in the app — are the exception: because that store is public they are stored Fernet-encrypted with `BACKUP_ENCRYPTION_KEY` (as `.enc`), or not stored at all when no key is set, in which case `/bills/scan` and `/purchases/scan` return `photo_url: null` (`backend/test_scan_encryption.py`). The app accepts both forms a record can hold — a server-relative `/uploads/...` path (local dev, older records) or a full https URL — via `AppConfig.mediaUrl`.- Rejected auth attempts (missing/invalid bearer token) and rate-limit hits are logged server-side (method, path, client IP) for basic abuse/intrusion visibility — see `backend/auth.py` and `backend/utils/rate_limit.py`.
- On Vercel the interactive API docs (`/docs`, `/redoc`, `/openapi.json`) are switched off — they would publish every endpoint and schema to anyone — and CORS allows no browser origins (the mobile app doesn't use CORS). Local development keeps both (`backend/config.py`'s `API_DOCS` / `CORS_ORIGINS`; `backend/test_prod_hardening.py`).

## 7. Technical Architecture

High-level components as implemented in the current codebase:

| Layer | Implementation |
|---|---|
| Client | Flutter/Dart. Key packages: `firebase_core` / `firebase_auth` / `firebase_messaging` (auth & push), `sqflite` (local offline queue), `shared_preferences` (local settings), `connectivity_plus` (reconnect detection), `pdf` / `printing` (invoice PDFs), `mobile_scanner` / `barcode_widget` (barcode scan & JazzCash QR), `url_launcher`, `share_plus`, `file_picker`, `flutter_localizations` / `intl` (20-language UI localization, generated from `lib/l10n/app_*.arb`). |
| Backend | Python FastAPI service, entrypoint `backend/main.py` (app creation, CORS, auth middleware, request-rate tracking/limiting, startup wiring only). Route logic lives in `backend/routers/` (one module per resource: customers, suppliers, bills, purchases, items, expenses, reports, gst, backup, settings, notifications, admin, users, search), shared logic in `backend/utils/` (barcode generation, GST/invoice-numbering math, PDF builders, settings lookup, CSV export, AI bill-scan extraction/matching) and `backend/migrations.py` (startup schema migration/backfill/seed, dialect-agnostic via `sqlalchemy.inspect` rather than raw `PRAGMA`; `ensure_schema()` runs all of it only when the fingerprint stored in the `schema_meta` table differs from this code's, so an up-to-date database costs one SELECT per start). SQLAlchemy-style models (`models.py`, `schemas.py`) over Postgres (Neon, `postgresql+psycopg://`) in production or a local SQLite file (`bookkeeper.db`) as fallback — `backend/database.py` picks the dialect from `DATABASE_URL`/`DATABASE_URL_UNPOOLED` (pooled connection for app traffic, direct/unpooled for DDL, per Neon's own guidance) and every dialect-sensitive query (barcode/invoice atomic counters, GST month filtering) branches on `IS_POSTGRES` rather than relying on SQLite-only SQL. Firebase Admin SDK (`firebase_setup.py`) is used server-side for user/account management. Google's Gemini API powers the AI Bill Scanner and AI Purchase Invoice Scanner (Sections 5.2/5.4, reading a bill or purchase invoice photo), the AI Morning Briefing, and Ask Your Shop, including the text-to-speech voice; every Gemini call is a plain REST request through one shared `httpx` helper, `backend/utils/gemini.py`, with no SDK. |
| Communication | REST over HTTP, JSON payloads. The API base URL is configurable per install (defaults to a local address, editable from the Admin Panel). |
| Local storage | On-device SQLite (`bookkeeper_local.db`) holds a read-only customer cache, a `pending_bills` queue for offline bill capture, and a generic `pending_writes` queue (method/path/JSON body) for every other offline create/edit (customers, items, suppliers, purchases, expenses, bill payment-status). |

## 8. Known Limitations
- Localization covers all screens, but some text is deliberately English: the Privacy Policy's placeholder values (date, owner, email), the Admin panel's Firebase setup steps, custom (non-standard) unit names and user-entered names/categories, the app name, AI-generated answers' amounts (always written as "Rs 1,234" so they can be read aloud), server activity-log and push-notification text, rare Chinese/Japanese/Korean characters outside the standard national character sets in PDFs (trimmed Noto Sans SC/JP/KR fonts are bundled, so such a character prints as an empty box), WhatsApp/SMS messages sent to customers and suppliers, printed label text, Android notification channel names, the biometric unlock prompt, the Notifications screen's test-run result lines and the STRN/JazzCash field validators. Error messages thrown by the sign-in service are translated on the login/sign-up screens only. The 19 non-English translations are machine-written and not yet reviewed by native speakers. Dates and numbers still use English formatting.
- Single database per deployment (Postgres in production, SQLite as a local-dev fallback); not designed for multi-branch or high-concurrency use.
- Backup/restore is app-native rather than `pg_dump`/`pg_restore`-based on Postgres (see 5.11) — a dump isn't restorable through generic Postgres tooling outside this app, and a restore always wipes and reloads every table (no partial/selective restore).
- Admin Panel and push notifications require manual Firebase project setup (service-account key, `ADMIN_EMAILS`) before they activate; without it, the app runs but those features stay off.
- AI Bill Scanner, AI Purchase Invoice Scanner, the AI Morning Briefing and Ask Your Shop (Section 5.7, including its read-aloud voice) all require a `GEMINI_API_KEY` configured server-side (a free-tier Google Gemini key from https://aistudio.google.com/apikey); without it, with an invalid key, or when the free quota is used up, the relevant endpoint returns a clear error rather than a bare failure (the app then falls back to the phone's own voice for reading answers aloud).
- Tax logic has been migrated off the original Indian-GST template to Pakistan's single-rate sales tax (STRN, no CGST/SGST/IGST split) as a structural/cosmetic cleanup — this is an internal bookkeeping report, not a confirmed match to FBR's official Sales Tax Return/Annex-C format, and live FBR e-invoicing/real-time transmission (required under SRO 1852(I)/2025) is not implemented, since it needs a licensed-integrator decision and a confirmed schema first. Currency display is Pakistani Rupees, shown as "Rs" (confirmed with user 2026-09-04). Payment QR generation was migrated off the original India UPI template to JazzCash (2026-09-16) — the QR now encodes the shop's JazzCash mobile number rather than a UPI deep link; there is no in-app "pay with app" launch button since JazzCash has no equivalent interoperable intent scheme, and no Raast/EMVCo-standard QR payload is generated (that would need verified spec data this migration didn't have access to).
- The Settings screen's Shop STRN field was removed alongside the (genuinely unused) shop-level GST/HSN defaults in the same 2026-09-16 cleanup pass — collateral removal, not a deliberate decision, confirmed and left as-is by the user on 2026-09-17. It remains live server-side (validated on `PUT /settings`, printed on invoices/ledgers), but there is currently no in-app UI to set/edit it — a shop needing to set or correct its STRN has no path to do so through the app.
- The Privacy Policy (Settings → Account, and `docs/PRIVACY_POLICY.md`) has the legal entity name, support contact email, and publish date left as `[PLACEHOLDER]` in both copies — added 2026-09-19, not yet filled in, and not reviewed by anyone with legal authority to represent the business. Don't treat it as ready to ship to real users until both are done.
